## Open decision boundaries

- Package manager: npm is used for the initial scaffold; changing package manager remains a future explicit decision.
- Backend/runtime: hiscores still needs an accepted production runtime/hosting model before public live availability can be claimed. This is not a blocker for the trusted-tester handoff while the manual level fallback remains clear. Market price refresh is now scheduled repo automation that writes static JSON, not a user-triggered backend sync path.
- Database: no decision to add one; market price refresh is explicitly file-backed JSON.
- Deployment: the current external sharing model is trusted-tester only. The target architecture is static-first and provider-agnostic for now; no final public release, hosting path or full CI/CD pipeline is accepted.
- Static-host security headers are recommended in operations docs for a real deployment, but no deploy target has accepted them yet and they are not required to start the trusted-tester handoff.
- Source data workflow: LostCityRS/Content is the primary target source for the current accepted game revision. The accepted generator entrypoint is `npm run data:generate`, reading `.sources/lostcity-content/` and overwriting `src/data/generated/source-pin.json`, the normalized current runtime snapshot `src/data/generated/game-data.json` and `docs/project/revision-impact/current.md`; the current script foundation validates source/output paths, applies generated-output hygiene checks and writes the first schema-valid foundation source pin, game-data snapshot and revision-impact report, while the authoritative parser and full hybrid calculation-impact suite are not present yet. Historical snapshot files are not part of the accepted model.
- Game data refresh workflow: revision bumps are accepted only through reviewed development PRs with generated snapshot diffs, validation, test/golden impact and explicit accepted calculation deltas. Automatic main-branch game-data updates are not accepted.
- Generated snapshot scope: v1 includes only current simulator-consumed domain data: monsters, items, equipment/weapons/ammo/spells, drop rows, planner/loadout requirements and provenance/warnings. It excludes raw upstream content, unused NPC/dialog/quest/world/map data, historical revisions and speculative future fields.
- Revision impact gate: `docs/project/revision-impact/current.md` must be committed in any revision bump PR and must summarize source refs, generator metadata, generated data diffs, representative calculation diffs, intentional deltas and validation results. Changed DPS, kills/hr, XP/hr, GP/hr or GP/XP outputs must be accepted or fixed before merge.
- Calculation-impact suite: the merge-blocking report section uses a curated representative suite seeded from existing golden/parity fixtures plus focused generated-data cases. A broad all-monster scan is included as an informational section and does not automatically block merge. The scan uses one fixed simple melee, ranged and magic baseline, with accepted notable-outlier thresholds for DPS/kills/hr/XP/hr over 10%, GP/hr or GP/XP over 25%, missing required data, warning-count increases and monsters entering/leaving the scan. The exact case file format and concrete item/spell/equipment ids are not present yet.
- Price update workflow: `markets.lostcity.rs`, scheduled-only refresh, latest JSON files and retained 12-hour history are accepted. The local writer and normalized fixture/input contract are present; the scheduler is GitHub Actions cron using `GITHUB_TOKEN` with `contents: write`, but the workflow and raw live upstream adapter are not present yet.
- Live integrations: [../technical/live-integrations-spec.md](../technical/live-integrations-spec.md) owns the target contract for hiscores and market prices; hiscores upstream and the exact market upstream response contract remain open questions.
- Hiscores upstream: the visible `https://2004.lostcity.rs/hiscores/player/index` HTML page is candidate evidence, but a possible API answer is pending and final direct-fetch/proxy hosting remains open.
- UI language policy: existing UI strings are English; documentation is now mostly Finnish.
- Rewrite setup persistence is versioned; a focused `sim_input_v3` setup-migration foundation is captured, while legacy planner UI state, market sync and full legacy `localStorage` migration fixtures remain open.
- Legacy Migration V1 implementation: D-042 accepts compatible import for the audited nested `sim_input_v3.monsterSetups` and `sim_input_v3.cannonByMonster` fields. Exact compatible field mapping, unknown-id handling and validation details belong to the implementation/test pass. `sim_planner_v1` and full legacy price-history payloads remain review-only/not migrated in V1; future import for either still requires an explicit decision.
- Cannon occupancy/overlay, cannonball cost and cannon ranged XP are ported into pure `src/domain/trip`; the dense rewrite dashboard exposes per-monster cannon controls, while final full-workbench placement remains open.
- Legacy source files are retained for fixtures/data bootstrap; deleting them requires a separate full-replacement decision.
- Final full-domain `SimulationResult` shape remains open until combat/equipment, trip/loot/supply and economy slices are composed for the UI.
- Dense spreadsheet can become the default root view during parity work; its final coexistence with the full tabbed workbench remains open.
- Planner item requirements are still a manual policy copied from the existing planner notes; they belong in the generated snapshot scope, but authoritative extraction and exact schema are not present.
- Future weapons are not added to canonical planner pools until a human accepts a product/data provenance decision.
- Historical multi-revision simulation is not accepted yet; the app targets one current accepted revision at a time.
